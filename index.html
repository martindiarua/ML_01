Abstract

This study asks whether page-level content signals can help a content team identify pages that deserve human review for a possible refresh or optimization. A constructed refresh-priority label marks a page when its click-through rate is below 7% and its engagement rate is below 40%; those two variables are excluded from the model features to prevent direct target leakage. The main model is logistic regression with median imputation and standardization, and it is evaluated against the Baseline established earlier in the analysis, using a held-out split that keeps client groups separate between training and testing. On the supplied test split, logistic regression measured 91.79% accuracy, 86.58% precision, 98.55% recall, and a 92.18% F1 score, while the Baseline measured 75.89% accuracy, 67.06% precision, 100.00% recall, and 80.28% F1. The baseline already caught every priority page in the test set, but at the cost of a high false-positive rate; logistic regression reduced false positives substantially while giving up only a small amount of recall, producing a meaningfully better F1 score. These results do not show that a refresh will increase traffic, rankings, conversions, or any other future business outcome. The resulting score is therefore used as a ranking signal for human review, supported by simple reason codes and an action playbook.

Research Question / Problem Statement

Large content portfolios can contain many pages competing for limited editorial attention. The practical problem is not simply finding pages with low performance; it is deciding which pages should be investigated first using measurable signals.

Decision supported: Which pages should the content team look at first? The model ranks pages for review. A person remains responsible for deciding whether a page should actually be refreshed, expanded, consolidated, redirected, or left unchanged.

Constructed refresh-priority label

A page is labelled as refresh priority when both conditions are met: CTR is below 7% and engagement rate is below 40%. This is a constructed decision label, not a directly observed business outcome.

Public-safe scope

Client-identifying information is not included in the public interpretation of the findings. Rows are excluded only where required fields are unavailable for a particular analysis. Missing numeric model inputs are handled through median imputation inside the modeling pipeline.

Leakage note: CTR and engagement rate define the target, so they are excluded from the logistic regression model's features to prevent the model from learning the label directly rather than genuine predictive signal. The Baseline is a fixed hand-written rule rather than a trained model, so it uses CTR directly as one of its scoring conditions — leakage does not apply to it the same way, since it isn't fitting parameters to the data. The client identifier is used for grouped validation only and is not included as a feature.

Methodology

The workflow is deliberately simple and interpretable: define the decision label, remove variables that directly define it, preprocess numeric signals, compare logistic regression with a simple baseline, and evaluate both on the same held-out client groups.

Model and preprocessing

The main model is logistic regression. Missing numeric values are median-imputed and the features are standardized before fitting the classifier.

Baseline and validation

The comparison baseline is a rule-based heuristic established earlier in the analysis. It scores each page using three conditions — click-through rate at or below 7% (+2), more than 90 days since the last content update (+1), and search volume above 20 (+1) — and predicts refresh priority whenever the combined score is at least 1. Because any single condition alone meets that threshold, the rule functions as an OR across the three signals: a page is flagged if it is low-CTR, stale, or in meaningful search demand. Both the baseline and logistic regression are evaluated on exactly the same held-out test set. A GroupShuffleSplit with client_id as the grouping variable keeps pages from the same client out of both training and test sets, reducing the risk of client-specific patterns inflating validation performance.

Results vs Baseline

F1 is the primary comparison metric because the review-ranking task needs a balance between identifying priority pages and avoiding unnecessary recommendations. Accuracy, precision, and recall are reported alongside it.

Interpretation

The 92.18% F1 score is evidence that, on this particular held-out client-group split and target definition, logistic regression separated the constructed priority class more effectively than the Baseline — not because the baseline missed priority pages, but because it flagged far more pages than necessary.

What it shows

The Baseline had perfect recall (100.00%) but only 67.06% precision: it caught every priority page in the test set (zero false negatives) but flagged 1,486 pages that were not actually in the constructed priority class, alongside 3,025 correctly flagged. This tracks with how the rule is built — flagging a page if it is low-CTR, stale, or in meaningful search demand is inherently broad, so it rarely misses a true priority page but also catches many pages that only meet one loosely-related condition. Logistic regression reduced false positives from 1,486 to 462 — a substantial cut in unnecessary review work — while giving up only 44 true positives (44 false negatives, recall falling slightly from 100.00% to 98.55%). That trade produced a meaningfully higher F1 score (92.18% vs. 80.28%).

What it does not show

The score is not a probability that refreshing a page will improve SEO, traffic, rankings, conversions, or revenue. It also does not establish that any individual feature causes the outcome. The model output should therefore be treated as a ranking signal for human review.

Limitations & Honest Framing

The results are useful for the decision defined here, but the scope of the claim is deliberately narrow.

  • Constructed target: The target is based on CTR and engagement thresholds; it is not a direct measurement of whether a page truly needs a refresh.
  • Observational data: Relationships in the data do not establish that changing word count, freshness, visibility, or another feature will cause better performance.
  • Dataset-specific validation: Performance may change for another portfolio, time period, population, or target definition.
  • Grouped validation is not perfect: Keeping client groups separate reduces one leakage risk but cannot remove every source of bias.
  • Score interpretation: The priority score represents model likelihood of matching the constructed label; it is not a probability of future improvement after a refresh.
  • Human judgment remains necessary: The model cannot assess factual accuracy, search-intent changes, brand requirements, business strategy, legal considerations, or the actual quality of a page.
  • Public interpretation: Findings should be described as observed, measured, directional, and decision-support signals rather than guaranteed outcomes.

The action playbook converts the model's ranking signal into a practical review workflow. The score determines ordering; reason codes provide simple context; a human decides the final action.

01

Refresh mature pages before they decay

Older pages with previous visibility are strong candidates for human review, especially when they are stale or declining.

02

Improve page-one click capture

Pages that already have visibility can be useful optimization targets. Improving titles, descriptions, relevance, and clarity may be more practical than rebuilding pages with little existing visibility.

03

Expand content when the page is genuinely thin

Longer content should not be treated as a target by itself. Expansion is most useful when a visible page is missing useful sections, examples, comparisons, definitions, or evidence.

04

Monitor AI referrals separately

AI referral traffic was small compared with total tracked sessions but showed a different page profile. It should be monitored as a separate visibility signal rather than treated as a replacement for organic search.

05

Use optimization flags as workflow signals

A flag does not mean a page is bad. A visible page with a measurable issue can be a better optimization candidate because there is enough evidence to investigate the problem.

06

Do not automate content decisions

The model should rank pages for review. It should not automatically rewrite, publish, delete, redirect, merge, or approve content.
